# ADR-0004：确定性重放与拓扑持久命名（TNP）的边界

- 状态：已接受
- 日期：2026-11-20
- 决策人：用户（阶段 review 的裁决）+ 主会话（文档与措辞落地）
- 关联：`docs/specs/entity-ref-contract.md` v0.2；
  `docs/adr/0003-entity-derivation-lineage.md`；
  `docs/reviews/2026-11-20-stage-review.md` §2.2

## 背景

`EntityRef` 契约（v0.1/v0.2）的验收线是"同一脚本重放两遍，实体 id 序列逐位一致；
tombstone 引用抛错；split/merge 谱系可解析"。README 与站点页曾把这件事表述为
"解决拓扑持久性引用难题"，这在工业 CAD 语境里是**过度声明**：

- **确定性重放（Determinism）**：同一脚本、同一输入顺序，重跑得到同一套 id。
  这是可复现性的最低要求，`EntityRef` 已经做到；
- **拓扑持久命名（Topological Naming Problem, TNP）**：参数化模型修改后
  （草图尺寸变化、增删特征），**引用要跟着语义实体走**。例如把草图宽度从 20 改成 50，
  原本"顶面右前边"仍是同一条边，即使它的 id、参数区间、甚至边的条数都变了。

两者差一整层：前者是"执行顺序稳定"，后者是"特征历史 + 邻接语义的稳定"。
工业界（Parasolid Tags、Onshape FeatureScript 的 `qCreatedBy`、FreeCAD Realthunder
的 ElementMap）都靠"哪个特征生成了它 + 它与哪些面/边相邻"来回答 TNP，而不是创建序号。

当前 `EntityTable` 按类型单调计数发号（`e0, e1, ...`），`RefMapping.split/merge`
记录单步派生关系。它解决的是**AI 单趟顺序生成脚本时的局部指针传递**，不是参数化
修改后的跨拓扑重生成。

## 决策

1. **收准对外口径**：`EntityRef` 承诺 **确定性重放 + 单步派生寻址（1-to-N / N-to-1）
   + tombstone 显式失效**；**不**承诺解决参数化 TNP。README、站点页、契约文档统一改口。
2. **TNP 列为独立阶段**（不进 P1）：未来实现需要
   - 特征历史锚点（`op_id` + 该操作生成的角色，如 `extrude:side[2]`）；
   - 邻接语义签名（相邻面/边的类型与相对位置，而不是全局计数）；
   - 上游参数变化后的候选重匹配与歧义显式拒绝（不猜最近实体）。
   该设计另立 ADR，不在本契约内偷偷扩展。
3. **验收线保持并写清边界**：现有"重放一致 / tombstone / 谱系可解析"三条继续有效，
   但新增一条文档级验收：任何对外材料不得把确定性重放表述为 TNP。
4. **不改变实现**：本次只改口径与文档，`kernel/entity_ref.py` 的 API 与行为不动；
   参数化 TNP 的 anchor 字段留待独立 ADR 设计，避免在契约层引入半成品。

## 被否方案

| 方案 | 否决理由 |
|:--|:--|
| 继续沿用"解决 TNP"的表述 | 对工业界读者是明显过度声明；一旦被问"改草图尺寸后 e7 指向谁"就穿帮 |
| 立刻把 id 换成特征历史锚点 | 需要先有特征树与重生成协议（P1 草图/拉伸尚未落地），现在做只能造出空壳 |
| 用"最近实体"启发式兜底 | 与全仓库"平局/歧义必须显式报错"的纪律冲突 |

## 后果

**正面**

- 对外主张与实现能力对齐，避免 review 时的可信度损耗；
- 把 TNP 的工程量显式隔离，P1 不被"看起来很小"的命名问题拖住；
- 后续做 anchor 设计时，边界与验收线已经写好。

**负面 / 风险**

- 需要改 README、站点页与契约文档的措辞，存在遗漏点；
- 用户可能仍期望"引用永远有效"——文档需要明确：**参数化修改不在当前承诺内**。

## 验收

- `docs/specs/entity-ref-contract.md` 增加"确定性重放 ≠ TNP"边界节；
- README §1/§2.4 与站点 `/x2cad/` 改口，不再声称解决 TNP；
- `python -m verify` 不受影响（仅文档与措辞变更）。
